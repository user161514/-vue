## 修复 `npm run build` 偶发失败：esbuild 删除临时文件 Access is denied

### 现象
Vite 3.2.11 打包时，模块转换和渲染都已完成，最后一步报错：

```
[vite:esbuild-transpile] remove C:\Users\Administrator\AppData\Local\Temp\esbuild-2ef9bdfa...: Access is denied.
error during build:
Error: remove C:\...\Temp\esbuild-2ef9...: Access is denied.
    at node_modules/esbuild/lib/main.js:801:29
```

### 诊断过程与结论
1. 残留文件 `%TEMP%\esbuild-<64位hex>` 手动删除**成功** → 权限、目录都没问题，是**构建当时的瞬时占用**。
2. 重跑 `npm run build` **一次就成功** → 属**偶发竞态**，不是必然失败。
3. 读 `node_modules/esbuild/lib/main.js` 源码确认链路：
   - 请求数据量较大时，JS 侧 `fsSync.writeFile` 把 payload 写到 `os.tmpdir()/esbuild-<随机hex>`（main.js:2176 `randomFileName`）；
   - 原生进程读完该文件后自行删除，删除失败就把错误文本回传，JS 侧在 main.js:801 `callback(new Error(error))` 抛出。
   - 报错栈指向 main.js:801 是**包装点**，不是删除动作本身（删除发生在 Go 原生进程里）。
4. 本机装有**火绒**（`HipsTray.exe` + `HipsDaemon` 服务在跑）。火绒实时监控在扫描系统 Temp 里新生成的临时文件时会短暂持有独占句柄 → 原生进程删除即失败。
   **根因：安全软件对系统 Temp 里 esbuild 临时文件的瞬时占用。**

### 已实施的修复
- 新建 `scripts/build.js`：构建前把 `TEMP` / `TMP` 指到项目内 `.tmp` 目录（不再用系统 Temp），并带**失败自动重试一次**（偶发问题的兜底）。
- `package.json`：`"build": "node scripts/build.js"`，同时保留 `"build:raw": "vite build"` 作为对照。
- `.gitignore` 增加 `.tmp`。
- 验证：`npm run build` 通过，系统 Temp 不再产生 esbuild 残留文件。

### 遗留 / 后续
- 真正治本：把项目目录 `.tmp` 加入**火绒信任区**（用户手动操作，火绒无可靠 CLI）。
- 长期可考虑升级 Vite（3.2.11 为 2022 年老版本，新 esbuild 对临时文件删除失败的容错更好），但属破坏性升级，暂不做。
- 若 dev 模式（`npm run dev`）也偶发同类报错，可同样处理；目前未观察到。

## nginx 初上手：启动后页面 404 的排查

### 环境现状
- 用户把 nginx 从 `D:\360安全浏览器下载\nginx-1.31.7` 移到了 **`D:\nginx-1.31.7`**（D 盘根目录），41 个文件完整。
- 用户在 `D:\nginx-1.31.7\html\` 放了自己的页面（`index.html` 429 字节 + `assets/`），想通过 localhost 预览。
- `conf\nginx.conf` 仍是官方默认配置，全部用相对路径（`root html`、`logs/...`），移动目录**不影响**。

### 根因：80 端口被 Steam++（Watt Toolkit）占用
- 现象：浏览器访问 `http://localhost/` 显示 **HTTP ERROR 404**（"找不到此 localhost 页"）。
- `logs/error.log`：
  `[emerg] bind() to 0.0.0.0:80 failed (10013: An attempt was made to access a socket in a way forbidden by its access permissions)`
  → **nginx 从未启动成功**，根本没有 nginx.exe 进程。
- `netstat -ano` 显示 80 端口 LISTENING 的 PID 是 **`Steam++.Accelerator.exe`**（Watt Toolkit / GitHub 加速器，
  路径 `D:\123pan\Downloads\github加速器\modules\Accelerator\Steam++.Accelerator.exe`）。
- 所以那个 404 页面是 **Steam++ 返回的**，不是 nginx 的。
- 原理：Steam++ 的 GitHub 加速会把 github.com 等域名解析到 127.0.0.1，并**占用本地 80/443 做反向代理**。

### ⚠ 沉淀为环境事实（以后复用）
- **本机 80 / 443 端口被 GitHub 加速器 Steam++ 长期占用**。任何想绑 80 的服务（nginx、IIS、其它 HTTP 服务）
  都会 `bind() failed (10013)`。以后遇到"服务器起不来/端口占用"，先查 Steam++。
- nginx for Windows **没有 GUI**，双击 `nginx.exe` 窗口一闪即退是正常的（它转后台）；
  启动失败的原因只写在 `logs/error.log`，看不到就是没启动成功。
- 解决方案二选一：
  1. nginx 改非 80 端口（保留 Steam++ 加速）—— 推荐；
  2. 退出 Steam++ 的加速功能再用 80。

### ✅ 端口处置（22:10）
- 采纳方案 1：`nginx.conf` 里 `listen 80;` → **`listen 90;`**（事前确认 90 空闲且不在 Windows 排除端口范围内）。
- `nginx -t` 通过 → 启动 → 90 端口 LISTENING。`curl http://localhost:90/` 返回 **200 OK / Server: nginx/1.31.7**。

### 用户真实意图（重要）
**用 nginx 部署 Vite 打包产物**：已把 `vue-project/dist/` 的 `index.html` + `assets/` 拷进 `D:\nginx-1.31.7\html\`，
通过 `http://localhost:90/` 访问 → 这是「Vue 打包 → nginx 静态托管」的练习线，后续上线流程可沿用。
- ⚠ 每次 `npm run build` 后要**重新把 `dist/` 内容拷进 `D:\nginx-1.31.7\html\`**，否则访问到的还是旧产物。
- nginx 常用命令（须在 nginx 目录下执行）：`start nginx` / `nginx -t` / `nginx -s reload` / `nginx -s stop`。

## nginx 部署 Vue SPA：接口「访问异常」的排查与修复（22:12）

### 现象
`http://localhost:90/emp` 页面能正常渲染，但右上角弹红字「接口访问异常」，表格「暂无数据」。

### 根因（三层证据链）
1. `src/utils/request.js`：axios `baseURL: "api"`（相对路径）→ 实际发出 `http://localhost:90/api/xxx`。
2. `curl http://localhost:90/api/dept1` → **404**。
   nginx `error.log` 铁证：`CreateFile() "D:\nginx-1.31.7/html/api/dept1" failed (3: ...)`
   → nginx 把接口请求当**静态文件**在 html 目录里找。
3. `curl http://localhost:8080/dept1` → **401**（后端 Spring Boot 正常，接口通，401 只是缺 token）。
→ **结论：Vite 的 `server.proxy` 只在 dev 生效；部署到 nginx 后必须自己配反向代理。**

### 已修复：nginx.conf 加两段
```nginx
location / {
    root   html;
    index  index.html index.htm;
    try_files $uri $uri/ /index.html;   # SPA 刷新 / 直达路由不再 404
}

location /api/ {
    proxy_pass http://localhost:8080/;   # 末尾斜杠 = 剥掉 /api 前缀，等价 vite 的 rewrite
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
}
```

### 验证（`nginx -t` 通过 → `nginx -s reload`）
- `/api/dept1` → **401**（转发成功，不再是 404）
- `/` → **200**
- `/emp` → **200**（try_files 生效）

### 关键知识点 / 待办
- **`proxy_pass` 末尾斜杠规则**：`proxy_pass http://host:8080/;`（带斜杠）把 `/api/emp2` 变成 `/emp2`；
  不带斜杠则变成 `/api/emp2`。与 `location /api/` 搭配时**必须带斜杠**，才与 vite 的 rewrite 等价。
- ⚠ 隐患：`request.js` 的 `baseURL: "api"` 是**相对路径**。当前页面在 `/emp`（单级）下解析成 `/api/...` 正常，
  但路由变成多级（如 `/emp/detail`）时会解析成 `/emp/api/...` → 404。**建议改成 `"/api"`（绝对路径）**。
- `error.log` 里 `.well-known/appspecific/com.chrome.devtools.json` 的报错是 Chrome DevTools 探测请求，无害。
